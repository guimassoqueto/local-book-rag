# Data Sharing and Model Output Checklist: Cloud models for chat and summaries, opt-in

**Purpose**: Test whether the requirements are complete, clear, consistent and measurable where the
feature is riskiest. For the first time, it sends book text to a third party (constitution I). It
reads a new model family's replies, citations and abstentions included (V, VII). It adds failure
and fallback paths, and it changes what `reindex-all` does with saved summaries (II). That is why
`AGENTS.md` makes this checklist a step of the flow. The choices, the configuration, the Research
tab, the success criteria, the records and the release are covered too.
**Created**: 2026-11-20
**Feature**: [spec.md](../spec.md), with [plan.md](../plan.md), [research.md](../research.md),
[data-model.md](../data-model.md), [contracts/](../contracts/) and [quickstart.md](../quickstart.md)

**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

**Resolution, 2026-11-20**: the owner answered four items. CHK006: the commands say what goes

## Failures and fallbacks

- [x] CHK013 Does the spec bound how long a failing model may hold a request before the next one
  starts? FR-017 names "times out" without a limit. The plan sets 120 s of silence in the profile,
  plus two SDK retries with their backoff (R4), and the owner waits through it for each failing
  model of a sequence. [Clarity, Gap, Spec §FR-017, plan Performance Goals]
  → The owner's answer: 120 seconds. FR-017 gives a silent model that long, once, never twice,
  and allows two quick retries after a rate limit, an overload or a lost connection only. R4
  turns the SDK's retries off, since they would retry a timeout and triple the wait.
- [x] CHK014 Is "withdrawn" defined for each surface? FR-017 says that a failed model's text MUST
  be withdrawn, and research R9 marks it on standard error in `ask`, where the text stays on
  standard output. Is that reading in the spec, or do FR-017 and R9 conflict?
  [Conflict, Spec §FR-017, research.md R9]
  → FR-017 says what "withdrawn" means in the tab (removed) and in a command (said discarded on
  standard error), and SC-008 checks both. R9 and the spec now agree.
- [x] CHK015 Is it intended that a misconfiguration, such as an allowed model that refuses the
  profile's effort (`rejected`), falls back on every request, showing only in each failure line and
  in `doctor`? Does any requirement ask for more, such as a startup warning?
  [Clarity, Spec §FR-017, §FR-021, research.md R12]
  → Intended, and now stated in the Edge Cases: such a model fails every request, each failure
  said, and the checks name what it refuses. No startup warning, since startup contacts no
  provider (FR-021, R12).
- [x] CHK016 Is it stated as intended that a request one provider declined, a safety refusal, goes
  on to the next model, possibly another provider's? And is the decline's category shown? FR-017
  lists "declines" among the failures; FR-018 shows a reason, not a category.
  [Clarity, Spec §FR-017, §FR-018]
  → FR-017 says a declined request goes on like any failure, and FR-018 shows the provider's
  category when it gives one (Edge Cases).
- [x] CHK017 Are the failed attempts' costs accounted for? FR-022 sums a cloud summary's tokens over
  its steps, those of the attempt that finished; a cloud attempt that failed late was billed for
  its steps too. Is leaving them out intended, and said? [Completeness, Spec §FR-022, §FR-019]
  → The owner's answer: count them. FR-022 gives each cloud attempt's tokens, a failed one's for
  the steps it finished (SC-007, R8, R10, `data-model.md`, `contracts/interface.md`).
- [x] CHK018 Do the spec's failures (FR-017) and the plan's reasons (research R7) match? The plan
  has `rejected` (a 400) and `outage` (a 5xx), which FR-017's list doesn't name; "can't be reached"
  covers only one of them. [Consistency, Spec §FR-017, research.md R7]
  → FR-017's list adds "is down or overloaded" and "rejects the request", matching R7's
  `outage` and `rejected`.
- [x] CHK019 Is the error after every model failed specified for a summary as for an answer, and
  does it say that the local model's own failure, such as Ollama being down, is listed last with
  the others? [Completeness, Spec §FR-018, §FR-019]
  → FR-018 lists every failure in order, the local model's last, for a summary as for an answer
  (`contracts/services.md`).
